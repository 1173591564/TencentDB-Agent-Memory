1猜想起点

为什么想做这个实验 —— 一条从架构讨论长出来的技术路线

在讨论 TencentDB Agent Memory 的 session-init 机制时，我们发现了一个架构级缺口：MemoryProxy 自身不托管任何 UI——它通过把客户端 LLM base URL 指向自身被接入（如 CC 的 ANTHROPIC_BASE_URL=http://proxy:8096/…，server.ts:177），以反向代理 + 伪造 AskUserQuestion tool_call 的方式弹身份表单：proxy 把伪造的 form 注入请求流返回给客户端，借用客户端自己的表单渲染器展示。但 dsh 的 headless 模式没有这类 UI 工具——它不挂 ask-user preset，agent-loop 会把未知工具直接校验抛出（handler.ts:706-714），所以 proxy 只能对 headless 请求 bypass，身份识别在这个场景下是缺失的。

由此引出核心猜想：dsh 官方宣传 "everything is plugins"，那能不能不必让请求流经 proxy 的转发层，而是写一个 dsh 原生插件，直接在 dsh 的 workflow 生命周期节点上插入 Tencent agent memory？如果原生插件跑在客户端进程内，它甚至可以自己解决交互问题——把身份表单外包给一个外部仪表盘。

实验命题dsh headless（无内置 UI 的一次性驱动模式）能否通过原生 Cordis 插件 + 外部浏览器仪表盘，把交互式人机问答与三元组身份识别完整搬到 dsh 进程内 —— 全程不改 dsh 一行源码。

两阶段验证策略

命题太重，拆成两阶段，每阶段有独立的成功判据：

阶段一（P0–P3）· 建筑地基
验证最底层的 architectural prerequisite：headless dsh 能否把 ask_user_question 工具的问答外包给外部浏览器仪表盘。LLM 调工具 → 插件 provider 收到 → SSE 推到浏览器 → 人点选项 → 答案回灌 → agent 继续。如果这层不通，后面全部免谈。
阶段二（P4-b）· 完整接入
在地基上复刻 proxy 的完整 session-init：身份识别状态机（asset_confirm → team → agent → task，含 auto-select / bypass）+ 持久化到 proxy SessionStore + <session_context> 注入 system prompt。数据走 Gateway，身份走 proxy。

2调研发现 · dsh 插件体系解剖

读 deepseek-harness 源码确认的扩展点全貌（关键证据 file:line）

插件形态：标准 Cordis 插件

dsh 的"插件"就是标准 Cordis 插件——npm 包导出 name / inject / apply(ctx, config)。官方设计 note 原话："native hooks are not a package — a native hook is just an ordinary Cordis plugin subscribing to the canonical lifecycle events"（.agents/notes/implemented/feature/2026-06-30-interception-extension-points.md:9）。preset 只是插件清单文件，加一行即挂载。

headless 的交互原理

dsh --profile headless "task" 不挂 Host/HTTP/浏览器插件，跑完任务即退出。userQuestions.ask() 把问题交给注册的 provider——谁注册谁就是 UI。web-app 场景是 apiproxy 注册 provider 把题经 WebSocket/SSE 送到浏览器；headless 默认无人注册 → NO_PROVIDER。这正给了外部插件接管的空间。

7实际使用

  • MemoryCore Gateway 运行在 127.0.0.1:8420（serviceId=default），元数据里有至少一个 team/agent

8踩坑实录

六个非显而易见的坑 —— 每个都消耗了真实调试时间，全部有源码级根因

#症状根因解法
1 补丁里的插件完全不加载，LLM 说"没有 ask_user_question 工具" cordis.patch.yml 的普通条目是对已有行的覆盖——id 匹配不到已有行时 applyEntryPatches 直接 warn+skip（cordis-plugin-include/src/index.ts:110-114） 新增插件必须用 - insert: 包裹（无 id 的 insert 顶层 push，对照 headless bundle 自己的写法 packages/bundle/headless/cordis.patch.yml:22-35）
2 阶段二初期：状态机还在弹第一轮 form，LLM 已经回复完毕 agent/session-start 是 emit（fire-and-forget），agent loop 不等 listener（agent-loop/src/index.ts:567） 状态机改挂 agent/pre-step waterfall（阻塞 LLM 请求直到表单答完）
3 provider 永不 resolve 时进程永久挂死（工具 promise 不被放弃） dsh 工具执行器"永不放弃已启动的 promise"（tools/index.ts:1529），且 ask_user_question 未声明 timeoutMs，无兜底 deadline 插件 provider 强制 10 min 超时 + 监听 request.signal abort
4 注入后 DeepSeek API 报 TRANSPORT: stream failed，exit 1 在 pre-step waterfall 里改写 messages 数组破坏了 dsh LLM adapter 期望的消息格式 放弃改 messages，改用 ctx.systemPrompt.section() 注册动态段（text 为函数，每次 assemble 取最新 session 状态）——注入后 exit 0
5 Gateway 调用 invalid_user_key / missing_user_key user_key 位置因端点而异：auth/verify 在 body；team/agent/task/list 需 header（x-tdai-user-key）+ body（user_key）双带（SDK metadata-client.ts:274,188,225） memory-client 统一在 header 带 user-key、body 合并 user_key
6 手动体验才暴露：agent 回复完、session-init complete 已打印，进程却卡住永不退出（自动化 e2e 跑不到——脚本答完题就断开连接了） headless 退出链 = io.exit() → shutdown.shutdown() → await 整个 cordis tree 的 fiber.dispose()（apps/cli/src/profile-boot.ts:210,257）。dispose 会关 dashboard-provider 的 HTTP server，而 Node 的 server.close() 会等所有 keep-alive 连接自然断开——浏览器开着仪表盘时 SSE 长连接（/events）永远挂着 → close 永不回调 → dispose 挂起 → 进程永不退出 close() 里先调 server.closeAllConnections()（Node 18.2+）强制断开 keep-alive/SSE 连接再 server.close()——修复后手动答题全程跑通、答完即退（exit 0）
7 每次都要手动开浏览器访问 :8790 才能答题，忘了开就卡到 10 min 超时 交互是"人看仪表盘答题"的，但 headless 无 UI 提示，答题入口没人提醒 dashboard-provider 加 auto-open：首个 pending 问题出现时用系统命令自动打开默认浏览器（win32 cmd /c start / macOS open / Linux xdg-open），仅触发一次；env DASHBOARD_AUTO_OPEN=0 可关（无人值守场景）
方法论坑 #1 和 #2 的共性：dsh 的事件语义（emit / waterfall / serial）和 patch 语义（insert / override）在文档里不显眼，读源码 + 对照官方 bundle 自己的写法是唯一可靠路径。这本身就是"everything is plugins"的隐性学习成本。坑 #6 的教训：keep-alive/SSE 长连接会让 server.close() 静默挂起——凡是"进程退出依赖 dispose 完成"的架构（cordis、Koa、优雅停机），插件里的 HTTP server 都要显式 closeAllConnections()。

9结论与展望

两阶段判据全绿 —— 架构路线的定论与下一步

核心结论

① "everything is plugins" 是真的
dsh 的原生扩展点（pre-step waterfall / systemPrompt.section / userQuestions.registerProvider / tools 事件）对外部插件完全开放。本实验全程零 dsh 源码修改——一个 examples 目录 + 一个 profile 补丁文件完成了全部接入。
② headless 身份缺口被缝合
proxy 在 headless 场景伪造 form 被拒的缺口，由进程内原生插件 + 外部仪表盘补上：状态机在 pre-step 阻塞弹表单，用户在浏览器答题，身份识别在请求离开进程前完成。
③ proxy 角色可以转变
身份识别与注入移入原生插件后，proxy 从请求流转发者（改 base URL 接入、拦截一切 LLM 请求的层）转为持久化后端 + prewarm 服务：本实验的 native-init 端点是第一步——插件选完三元组 POST 给 proxy 落 SessionStore，proxy 与原生插件共享同一份会话状态。
④ 与 OpenClaw 插件同构
本实验的形态与 MemoryCore/openclaw-plugin（hooks + SDK 委托 Gateway 的框架适配层）完全同构——验证了这条路线在不同 harness 间的可复制性。

下一步（未做）

  • P4-a · proxy 语义缝合验证：dsh 挂上 ask_user_question 工具后走 proxy(:8096)——handler 的 bypass 判定（agentSource=dsh 且 tools 不含 ask_user_question，handler.ts:706-714）将不再命中，proxy 伪造的 session-init form 会以合法 tool_call 进入我们的 provider，两条身份链路的交互值得单独验证
  • 完整 prewarm：注入目前只做 <session_context>（[Agent]/[Task]），prewarm 链路（skill listing / knowledge / L2 场景索引 / L3 画像 / <tdai_memory_tools>）尚未搬到插件——Gateway client 已就绪，照 proxy 的 injector 清单逐个补即可
  • L0 会话捕获：session/event（只读）+ agent/turn-stopping 可承担 proxy 的写 L0 职责，让记忆闭环完整落地在原生侧
  • 生产化：native-init 端点加鉴权；状态机补 retry/maxRetries 强制 bypass；SDK 正式接入替代手写 client
一句话总结从"DSH 能否原生接入 workflow 节点"的猜想出发，两阶段实验证明：dsh 原生插件 + 外部仪表盘，是 headless dsh 接入腾讯 agent memory 的可行完整路径——身份识别、表单交互、持久化、上下文注入全链路原生实现，proxy 退居持久化与预热服务之位。
