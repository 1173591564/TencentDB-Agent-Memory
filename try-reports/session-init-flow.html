1整体定位

Session Init 发生在哪里、解决什么问题

Session Init 发生在 MemoryProxy，不在 coding agent 里，也不在 MemoryCore 里。它解决的问题是：当一个 AI 客户端（Claude Code / CodeBuddy / opencode / Codex / WorkBuddy / DSH）第一次发起对话时，proxy 还不知道这个会话归属于哪个 team / agent / task —— 而没有这三元组，后面的记忆注入（L1 召回、L2/L3 注入）、知识库注入、L0 写入全都无法做租户隔离。所以 session init 的任务就是在对话真正转发给上游模型之前，把 (team_id, agent_id, task_id, user_id) 这套身份确定下来并持久化。

关键 coding agent 是多租户共享的通用客户端 —— 同一个 claude code 二进制可能今天连这个 proxy、明天连那个 proxy，agent 自己不该持有"我属于哪个 team/agent/task"的状态。这份身份是 proxy + kernel 的租户视角，必须由 proxy 在请求入口拦截建立，然后注入到 prompt 里喂给 agent。agent 只看到结果（<session_context> 块、<tdai_profile_memory> 块等），不知道这些是哪来的。

关键设计点

  • 递进 auto-select：init.ts:920-981，team=1 + agent=1 + task=1 时全自动跳过所有 form，直接完成注册——单租户单 agent 场景用户零感知
  • 分页：Claude Code 的 AskUserQuestion 限 2-4 选项，codex 的 request_user_input 限 3 选项；候选超限时每页展示 N 个 + "更多→"选项，用户点"更多"则 agentPageIndex++ / codexPageIndex.agentPage++ 重发同 stage form
  • maxRetries 兜底：每个 pending 阶段连续未识别 config.maxRetries 次后强制 bypass，避免卡死
  • SKIP 词 bypass：用户在任意选择阶段输入"跳过/不关联/skip"主动 bypass
  • 多客户端适配：session/index.ts:100-203 是路由 wrapper，按 agentSource 分派到 CB 状态机或 CC 状态机；WorkBuddy / DSH 复用 CB 状态机但外层重渲染 form

6completeRegistration 做了什么

状态机的终点站 init.ts:357-488

  1. 校验 task 缺失策略（taskMissingPolicy）：reject → bypass；default → 用 defaultTaskId 占位；skip → 无 task 注册，仅 agent 级注入
  2. buildRegistrationData：从 cachedTeams 里反查 agent 所属 team_id，组装 SessionRegistrationData
  3. 拉详情：并发 metadataClient.getAgent() + getTask()，拿到 agent 的 prompt/persona 和 task 的 goal/description——这俩就是后面要注入 system prompt 的内容
  4. buildSessionInfo（registrar.ts:20）：本地构建 SessionInfo（不再调 TMC 的 POST /sessions），写入 SessionStore（L1 内存 + L2 Redis/SQLite）
  5. appendParticipationLog：fire-and-forget 记一条参与日志到内核
  6. applyArtifactsAndContext：调 injectSessionContextWithToggles 把 <session_context> 块（Agent id/name/prompt + Task id/name/goal）塞到 system message 末尾

7注册完成后的连锁反应

回到 anthropicHandler.ts:814-864，justRegistered=true 时

  1. fetchAssetCapabilities：拉该 user 在内核里的资产能力旗标（chat_memory / llm_wiki / code_graph 各自 on/off），后续 injector 按旗标决定是否 emit
  2. prewarmFromConfig（injection/prewarm.ts）：同步 await，对所有 cacheStrategy = "session_init" | "hybrid" 的 injector 并行跑 hook.prewarm()，把结果写进 HookCacheRepo（COS）。默认 20s 超时，单 hook 失败静默 skip。这一步的意义是：首轮对话的 injection pipeline 能直接命中缓存，不会出现"第一轮注入 0 块"的空窗
  3. 之后每轮请求，injection pipeline 从缓存读 prewarm 结果 + miss 时走 execute() 兜底
每轮行为 session 一旦 initialized，后续请求进 handleSessionInit 直接命中 Case 3：从 store 读出 sessionInfo / agentDetail / taskDetail，每轮重新注入 <session_context>（客户端每次发的是干净 messages，proxy 必须每轮重新塞）。bypassed=true 的 session 只 strip 不 inject。

8三元组各字段的用途

Session Init 三元组（team / agent / task）—— 全部用户定义；team + agent 必需，task 可选

agent_id强制
  • 记忆 owner：L0/L1/Profile 的强制隔离键（isolation.ts:20），缺 teamId 或 agentId 直接抛错
  • L3 persona 注入：agent.prompt 整段塞进 <session_context>
  • L2/L3 profile 聚合键：profile 是 team+agent 级聚合
  • 跨 agent 借入锚点：resolveFixedAssetCtxs 用 agentId 查 agent-fixed-asset 绑定，找借入的 chat_memory
  • 知识库 per-agent 绑定：listAgentKnowledgeIds(agentId, userKey)
team_id强制
  • 归属/可见性边界：知识库 wiki/codegraph 按 team 列全量
  • 借入记忆的 team 一致性校验：只接受同 team 的借入 agent
  • L2/L3 Profile 归属键：(teamId, agentId) 定位 profile
  • clearMemoryContent：要求 teamId + agentId 都非空
  • 参与日志四元组之一
task_id可选
  • 任务上下文注入：Task goal/description 注入 system 的 [Task] 段
  • L0/L1 可选业务过滤维度：IsolationFilter.taskId 存在时 WHERE 加 task_id = ?
  • taskMissingPolicy：没选 task 时 reject/default/skip 三策略
  • 参与日志记录：仅在有 task_id 时才记
  • 不用于 L1 提取触发：L1 提取是 session-based，task 不能替代 session

两个三元组的区分

项目里有两个不同的"三元组"，都叫三元组但成员不同：

三元组成员场景出处
Session Init 三元组team / agent / tasksession 注册时让用户选的身份INSTALL_CN.md:102
Isolation 三元组team / agent / userv3 API L0-L3 接口强制校验的隔离维度v2-router.ts:121

两者重叠在 team + agent 上：team_id / agent_id 共用；Session Init 三元组多 task_id（用户选），Isolation 三元组多 user_id（鉴权自动解析）。

9哪些用户定义，哪些自动注入

身份字段的来源分工

字段来源机制
team_id用户定义x-tdai-team-id header 预选，或 form 里从 listTeams 选
agent_id用户定义x-tdai-agent-id header 预选，或 form 里从 listAgents 选
task_id用户定义（可选）x-tdai-task-id header 预选，或 form 里选；缺省走 taskMissingPolicy
user_id自动（鉴权解析）Authorization: Bearer <user_key> → verifyUserKey() → 内核 /v3/meta/auth/verify 返回 user_id
session_id客户端带或 proxy 分配autoConversationId 开启时 proxy 按 per-key / per-key-msg 策略自动生成；客户端带 conversationId 时用客户端的
透明 数据面向 memory-core 发请求时，proxy 的 tdai/client.ts:280-285 把这套身份自动塞进 x-tdai-* header，对客户端透明——客户端只要在 session init 时选一次，之后每轮都不用再带。
