核心结论（TL;DR）

sid 的本质是 proxy 的「跨轮挂载点」，不是 agent 生态的事实。它只需要满足三条功能要求——跨轮稳定、会话区分、可持久化——而不必等于 agent 的真实 sid。因此「构造」优于「寻找」；而任何锚定在消息内容（首条 prompt / 摘要）上的 sid 都会在 compaction 下失效。最终收敛到：账户/keyId/工作区 这类「会话级不变量」做锚点 + 持久化 + 抗 compaction 兜底，在 autoConversationId 这一环增强，不碰 compositeKey / session-init 状态机 / 三元组归属。

一问题定义

会话 id 是 agent 客户端自己构造的「对话线程索引」，但上游 LLM 协议本身无状态、无 session 字段。于是有的 agent 请求里不传 sid，导致依赖跨轮关联的 proxy 层拿不到它。

proxy 的接入机制是「改发送地址的转发代理」——agent 的 base_url 被指向 proxy，请求目标就是 proxy，proxy 做身份识别 + 注入后转发给真实 LLM。不是 MITM 嗅探，但业务层对双向流量有控制权。

sid 在 TencentDB 里的唯一用途：作为 compositeKey = ${agentSource}:${sessionKey} 的 sessionKey 部分，充当 SessionStore 的 Map key，承载「记忆—身份—状态」的挂载。它需要满足三条功能要求：

① 跨轮稳定：同一会话的每轮请求 key 一致（否则状态机、L0-L3 全断）
② 会话区分：不同会话不撞（否则记忆串了）
③ 可持久化 + 可反查身份：跨重启/pod 能恢复，能反查回 team/agent/task 三元组

关键洞察：这三条没有一条要求「sid 等于 agent 的真实 sid」。agent 的真实 sid 只是恰好满足三条的一个来源，不是唯一、更不是必须。

二五个关键发现

发现 1 · sid 归属 agent 生态

session id 是 agent 生态的自有概念，TencentDB 只是「借用」它做挂载点，不是发明者。

发现 2 · 工具面没有「查询 sid」的工具

穷举 <tdai_memory_tools>（6 个只读工具）、skill-bridge、memory-bridge、meta 端点——全是「消费 sid」或「skill CRUD」，没有 get-session / list-sessions。sid 是「约定共享的秘密」，由 proxy 渲染工具模板时写死注入（x-conversation-id: {sessionId}），无需查询。

发现 3 · sid 与 ask-question 的因果

不是「为了调用 ask-question 所以要 sid」，而是 sid 是跨轮状态关联键（session-init 状态机 pending_* → initialized 必须跨多轮存活），ask-question 只是状态机借用的交互载体。没有 sid → 表单循环当场断。

发现 4 · 不传 sid 的根源

agent 无会话概念（无状态脚本/单轮），或有但不带出（协议没这字段 / 刻意不暴露）。传是自定义扩展，不传是协议默认。

活标本：WorkBuddy 自己。它内部有 sid（env CODEBUDDY_SESSION_ID 实测可达），但发请求时大概率不把 sid 带进 header（抓包独有 header 集合无 sid，且 workbuddyHandler.ts:875 有 ${keyId}:${traceId} 降级）——正是「有 sid 但不带出」。

发现 5 · proxy 的降级链与代价

详见下一节的精确拆解——原始表述「一条链」是错的，实际是两条独立链 + 一层被漏掉的 autoConversationId。

三降级链的精确拆解（含纠错）

最初把降级链写成 conversationId ?? profile.sessionKey(headers) ?? ${keyId}:${traceId}，这是把两个 handler 的两条独立链缝合成了不存在的一条。实际是：

链 A — OpenAI handler（CB / dsh，handler.ts:663）

resolveConversationId（6 header） → profile.sessionKey(headers) → 裸 keyId → autoConversationId mint/reuse

链 B — codex / workbuddy handler（codexHandler.ts:352-353）

extractCodexSessionId → ${keyId}:${traceId}
关键纠错：${keyId}:${traceId} 里的 traceId = uuidv7()（codexHandler.ts:281）每请求新建，所以它是「每请求必变」的伪 key，跨轮 compositeKey 永不命中——「能转发，不能记忆」。而链 A 的裸 keyId 是跨轮稳定的。

「能记忆」的判据不是「有没有 sid」，而是「降级 key 是否跨轮稳定」

降级层跨轮稳定性能转发能记忆
显式 sid稳定✅✅ 精确
裸 keyId（链 A fallback）稳定✅⚠️ 能记但会串（同 key 并行会话合并）
${keyId}:${traceId}（链 B fallback）每请求变✅❌ 必断
autoConversationId稳定但受限✅⚠️ 能记，但纯内存、不回传、TTL 30min、串并行

四方案探索历程

4.1 两阶段 sid 探测 否决

复用 session-init「伪造 form + 不转发上游」机制，第零轮让 LLM 用 agent 的 bash/read 工具找 sid、固定格式回传 proxy。

opik trace 实证（try-reports/opik-trace-report.html）：agent ↔ 上游 LLM 所有通信经 proxy；LLM 的 tool_call 经 proxy 回 agent、工具在 agent 侧执行（ReadTool.execute），tool_result 下轮经 proxy 回 LLM。所以「LLM 通过 agent 通用工具间接访问 agent 本地资源」是成立的。

WorkBuddy 自身实测：env | grep -i session 一行命中 CODEBUDDY_SESSION_ID，且能靠「jsonl 实时写入 + 时间戳」确认是当前 session。

否决理由：① 依赖 LLM 探索，不可靠；② env 探测会带出 Bearer token（安全副作用）；③ dsh 进程内 sid 通用工具够不到；④ 本质是 autoConversationId 的「value 来源升级」（mint 伪 UUID → 探测真实 sid），而非「让 session-init 能跑」的前提——而后者 autoConversationId 已覆盖。

4.2 构造 vs 寻找 结论：构造更优

维度构造 sid（autoConversationId 思路）寻找 sid（两阶段探测）
依赖零（不依赖 agent 发 header / 落盘 / LLM）依赖 LLM 探索 + sid 落盘
确定性纯函数/分配器LLM 能力，不确定
延迟零多一轮
泄漏风险无env 探测带 token
通用性所有 agent进程内型（dsh）除外

sid 是 proxy 的需求，不是 agent 的事实；满足需求靠「构造」就够了，「寻找」是过度设计。

4.3 compaction 死穴（内容型 sid 的致命伤）

开源 PR #1138（Cursor 适配器）提出「首条 user prompt hash」构造 sid：

sid = "cursor-" + sha256( JSON.stringify([body.user, 首条 block 型 user 消息 content]) ).hex.slice(0,32)

这本质是 autoConversationId 的 per-key-msg 单 agent 特化。它的致命问题是怕 compaction——compaction 恰恰丢弃首条 prompt。

主流 agent 的 compaction 行为

agentcompaction 机制首条 prompt 保留吗
Codex CLI「用户消息神圣不可侵犯」：只删 assistant/tool，保留所有 user 消息✅ 保留（local path）
Claude Code/compact 用摘要替换整个历史❌ 丢（压进摘要）
Cursor / Cline摘要作为新会话起点❌ 丢
OpenCode可逆隐藏 + 回放最后一条 user❌ 只回放最后一条
摘要的「角色/位置」本身也不统一：codex local 是 user 角色（_summary 前缀）、codex remote 是 AES 加密 blob、Claude Code 旧版 TS 是 user（isCompactSummary:true）、新版 Rust 重写后是 system（带 compact_boundary）。同一 agent 的摘要角色都跨版本变过——这是内部实现细节，不是可依赖的协议约定。
因果链闭合：历史单调累积 → 撞上下文窗口 → compaction → 丢首条/改写摘要 → 内容型 sid 失效。任何锚定在消息内容上的 sid，都站在这条会被 compaction 改写的链上。

五锚点选择的两个必要条件

一个能当 sid 锚点的东西，必须同时满足：① 在每轮请求里（proxy 拿得到）+ ② 跨轮稳定（不变）。

候选锚点① 在请求里② 稳定结论
首条 user prompt✅（历史每轮重发）❌（compaction 丢）不可靠
compaction 摘要✅（历史里）❌（每次 merge 变）不可靠
session 标题❌（只在 title-gen 出现一次）✅不可达
账户 / keyId / 工作区✅（header/body/system）✅✅ 唯一双满足

标题的问题是「对称但方向相反」：首条/摘要「在请求里但不稳定」，标题「稳定但不在请求里」。账户/keyId/工作区是唯一「既在请求里、又稳定」的——会话级不变量。

六最终 solution：S1 + S2 + S3

约束：不改核心架构与设计思路（sid 仍是 compositeKey 跨轮键、session-init 状态机不变、记忆按三元组归属不变、push 注入不变）。solution 只能落在「agent 不传 sid 时，sessionKey 如何稳定构造」这一环 = autoConversationId（conversation-allocator.ts）的增强。

S1 — 持久化 allocator 解「跨重启/pod 丢」

conversation-allocator.ts 的 byAlias / lastActive 是纯 Map，进程重启全丢、多 pod 各存各的。解法：落到 Redis/SQLite，复用 SessionStore 的 L2 存储层，只换存储后端，不碰 key 语义。

S2 — 不变量升级 解「per-key 串并行」

alias 从 keyId 升级成 keyId + X-User-Id/body.user + workspace_folder（identity.ts 已提取）。这些是「账户/工作区级不变量」，比 keyId 细、且抗 compaction，能分开「不同工作区的并行会话」。

S3 — 抗 compaction 指纹 解「per-key-msg 怕 compaction」

firstUserFingerprint（取首条 hash）改成「最近 N 轮滚动指纹」——compaction 专丢最老、不动最近 N 轮（保护区），故滚动指纹抗 compaction。仍不能区分「最近 N 轮内容相同的并行会话」，但把脆弱点从「必被 compaction 打」挪到「极少数极端场景」。

诚实边界

S1+S2+S3 能做到「优化常见路径 + 兜底极端场景」，不是完美解决。同账户、同工作区、真正并行的多个会话仍无法区分——这不是工程没做够，是信息论约束：无 header 的请求流里，没有信息能区分「同账户同工作区的两个并行会话」。
